  O QUE MUDOU no port (não foi find-replace):
  O Chroma é mais GRANULAR que o Prism — onde havia um .token.string existem
  .s .s1 .s2 .sd .se .sh …. As classes finas foram agrupadas nos mesmos BALDES
  visuais (distinguir dez variedades de string não ajuda ninguém a ler código).
  Ganhamos dois tokens que o Prism não tinha: .gp (prompt `$` de sessão de
  shell) e .go (saída de comando) — ambos tratados como ANDAIME.
  O .err foi NEUTRALIZADO: o default do Pygments pinta erro de lexer em
  vermelho com borda, o que salpica o bloco de alarme falso quando o lexer só
  conhece a linguagem pela metade.

  BUG HERDADO DO PROTÓTIPO, corrigido aqui (medido nos 8 temas × 15 tokens):
  o .token.function usava var(--accent-dim), que mistura accent com o
  BACKGROUND (escurece). Sobre o --sidebar-bg do bloco ele AFUNDA: reprovava
  4.5:1 em quatro temas (jabuticaba 2.87, zuko 3.27, c64 3.39, ametista 3.62).
  Nunca apareceu porque o Lighthouse só mede o tema DEFAULT. Corrigido
  misturando com o FOREGROUND (clareia): color-mix(accent 85%, foreground).
  Comentário subiu de 55% p/ 60% (media 4.48 no tema `hacker` — reprovava por
  um fio). Estado final: 120 pares medidos, 0 reprovados, pior caso 5.00:1.
  -> LIÇÃO GERAL: --accent-dim sobre --sidebar-bg é uma combinação suspeita.
     Vale auditar os outros usos de --accent-dim no site com o mesmo método.

Pedido do Nilton (2026-07-12). A tese: CATEGORIA é o eixo EDITORIAL — poucas,
fixas, estáveis (a "seção" do arquivo). TAG é o assunto — muitas, livres,
acumuláveis. Um post PERTENCE A uma categoria e FALA SOBRE n tags.

No Hugo as duas são a mesma máquina (ambas `taxonomies`), e term.html/terms.html
já servem as duas sem código novo. O custo real não é técnico — é editorial.

  DECIDIDO:
  [x] cardinalidade: EXATAMENTE UMA categoria por post.
        É o que dá sentido a "mais fixa que as tags": vira eixo de navegação
        confiável e o post-card pode exibi-la como rótulo único (não lista).
        -> o build tem que VALIDAR: nenhum post sem categoria, nenhum com duas.
           (Hugo não impõe cardinalidade — a checagem é nossa, no template ou
           num hook de pre-commit.)

  EM ABERTO (decidir COM o Nilton quando o bloco chegar — não assumir):
  [ ] quais são as categorias? o vocabulário fechado precisa existir antes de
        qualquer post ser marcado.
  [ ] onde a categoria aparece na UI? candidatos discutidos, nenhum escolhido:
        - rótulo no post-card e no single (forma DISTINTA do chip .tag — os dois
          eixos não podem se confundir visualmente)
        - itens fixos na nav da sidebar (é o que explora serem poucas e estáveis)
        - página índice /categorias/ (pode ser redundante se já estão na nav)
        - na palette / filtro do Pagefind (acopla ao Bloco 2)
  [ ] idioma das URLs: /categorias/ (pt, consistente com o site) vs /categories/
        (default do Hugo, consistente com o /tags/ que JÁ está no ar e linkado).
        Se for pt, decidir se /tags/ também migra (/marcadores/?) — misturar os
        dois idiomas nas rotas é o pior dos mundos.

BLOCO 9 — DEPLOY (GitHub Pages)                << POR ÚLTIMO, DE PROPÓSITO
------------------------------------------------------------------
Decisão do Nilton (2026-07-12): deploy fica para o fim. Nada aqui bloqueia o
desenvolvimento local — mas TUDO aqui bloqueia o site funcionar no ar.
Decisão do Nilton (2026-07-13): o host é GITHUB PAGES, não Cloudflare Pages.
URL: https://cronistaterminal.github.io/  (já fixada no hugo.toml — Bloco 6)

  NÃO É PROBLEMA (registrado p/ não ser levantado de novo): o nome da PASTA local
  é temporário e irrelevante — o que decide a URL é o repo/origin, e o Nilton
  aponta a origin corretamente. Serve na RAIZ (site de usuário/org), não em
  subpath — que é o que mantém os paths absolutos (/icons/, /logo/) funcionando.

  [x] baseURL real   -> FEITO no Bloco 6.

  [ ] GITHUB ACTIONS — a diferença REAL para o Cloudflare.
        O CF Pages tinha build nativo (você dava o comando na UI). O GitHub Pages
        NÃO constrói nada: ou você publica HTML pronto, ou monta um workflow.
        Então o `just build` precisa virar um .github/workflows/*.yml:
          hugo (EXTENDED, versão pinada) -> npx pagefind --site public -> deploy
        Passos: actions/configure-pages, actions/upload-pages-artifact (public/),
        actions/deploy-pages.

  [ ] NODE no workflow — o build MUDOU no Bloco 2 e exige `npx pagefind`.
        Se subir sem isso: o site vai ao ar com a palette em ESTADO ZERO e a busca
        MORTA ao digitar (o import de /pagefind/pagefind.js dá 404; o palette.js
        degrada suave e mostra "busca indisponível", mas busca não existe).

  [ ] HUGO_VERSION pinada no workflow = a do `hugo version` local
        (hoje: v0.164.0+extended+withdeploy). Tem que ser a EXTENDED.

  [ ] .nojekyll — VERIFICAR, não assumir. O GitHub Pages roda Jekyll por padrão,
        e o Jekyll IGNORA arquivos/pastas que começam com underscore. Publicando
        via artifact (actions/deploy-pages) o Jekyll não entra no caminho; via
        branch gh-pages, entra. Confirmar qual caminho usamos e, na dúvida, um
        .nojekyll na raiz do public/ custa nada.

  [ ] /pagefind/ servido corretamente — CONFERIR NO AR, não assumir.
        O GitHub Pages NÃO permite custom headers (o CF permitia). O Pagefind
        carrega .wasm e binários do índice; se o Content-Type de .wasm vier
        errado, a busca morre em produção e passa no local. Testar a busca DEPOIS
        do deploy, não só no preview.

  [ ] 404 — sinergia com o Bloco 6: o GitHub Pages serve /404.html
        automaticamente. Fazer o do Bloco 6 já resolve este.

  [ ] domínio próprio / DNS — só se sair do …github.io (CNAME + config).
